Drawing 02 · the loop

One spec in, merged cards out

Write a spec as an issue and label it spec. Time splits it into cards with dependencies, runs them one at a time, and pulls the next card the moment one merges. Every step is a comment on the card, so the ledger is the issue thread itself.

Seats

@mention a model

Write @grok, @kimi high or @qwen max in any issue or PR and that seat answers in the thread. Only you and your collaborators can summon them.

Hands

The worker codes

A seat edits the repo on its own branch, runs the tests on a runner, and opens the PR itself. Workflow files and secrets stay out of its reach.

Updates

One engine, many repos

Every copy gets a weekly pull request with the latest engine from teahubxyz/time, the way a CMS updates itself, so projects don't drift.

Drawing 04 · start

Running in four steps

  1. Use the template. Create your copy of teahubxyz/time; it's yours, public or private.
  2. Give the seats a key. gh secret set VENICE_API_KEY
  3. Turn it on. gh variable set TIME_MODE --body live, TIME_WORKER --body "venice:qwen coder", TIME_REVIEW --body venice:grok, and TIME_AUTOMERGE --body on when you're ready to let it merge.
  4. Write a spec. Open an issue that lists the cards, each with a DONE: line, and label it spec. Watch the thread.

Or open your copy in Claude Code and say "set up Time": the setup skill in .claude/skills/time walks through it, and the Doctor workflow checks labels, settings and keys.

Drawing 05 · tolerances

Honest limits

  • The seats are as good as the models behind them. Small, well-scoped cards with a clear DONE: line work best.
  • You pay Venice for the seats. GitHub's runners are free for public repos and metered for private ones.
  • GitHub won't let Actions edit workflow files, so changes there (and anything under paths you protect) wait for a human.
  • Dry-run is the default and there is a daily cap; turning on auto-merge is your call, per repo.
  • On a public repo, only you and your collaborators can trigger seats or count as a reviewer. Never attach a self-hosted runner to a public repo.
  • It's young software: the engine changes weekly, and the update pull request tells you what changed.
